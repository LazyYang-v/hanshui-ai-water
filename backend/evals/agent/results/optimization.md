# Agent 性能与统计语义优化验收

日期：2026-11-07。实现已重建并部署到本地 API。实际模型始终仅为 `deepseek-flash`，运行数据全部来自模拟器。

本次范围：完整模型计时、同批工具有限并行、第二轮规划关闭思考，以及服务端计算并生成统计陈述。没有实施新的告警规则、视觉巡检或前端。

## 性能对照

固定问题：“黄官镇2026年11月6日是否有氨氮超标？请结合当时的DO、进水量和鼓风机状态分析可能原因，并给出核查建议。”优化前后各连续请求两次，分别新建会话。

| 指标 | 优化前 | 最终版本 |
| --- | ---: | ---: |
| 第一次端到端耗时 | 65.318 秒 | 35.587 秒 |
| 第二次端到端耗时 | 70.399 秒 | 38.176 秒 |
| 平均端到端耗时 | 67.858 秒 | 36.882 秒 |
| 平均 prompt tokens | 23697 | 23723 |
| 平均 completion tokens | 9581 | 7887 |
| 平均总 tokens | 33278 | 31610 |
| API 可答结果 | 2/2 | 2/2 |

平均端到端耗时减少 **45.6%**，平均总 tokens 减少 **5.0%**。最终两次均同时调用统计、Text2SQL 与 RAG，工具全部成功；三类引用、原因假设/建议的证据，以及已知设备计数检查均通过。第一轮回答首轮通过，第二轮回答因单条数据引用 10 项超过硬上限 8 项而修复一次，耗时与 tokens 已计入。

第二轮规划分别为 958.6 / 1012.1 ms，均明确 `thinking=false`。首轮沿用厂商默认。最终两次 `llm_ms` 分别为 47543.7 / 52800.3 ms，可以大于整轮墙钟时间，这是并行调用耗时相加所致。实际用户等待时间看 `total_ms`。

样本仅各两次，不报告 P95。厂商负载、模型采样和连续请求缓存会影响数字；这次比较包含并行、思考开关、固定统计与提示词调整的组合，不能把降幅全部归因于某一项，也不等于普遍性能保证。token 为应用记录的 usage，不能直接换算为完整账单。

## 实现与计时口径

- 网关保留原 `latency_ms` 为最终成功的单次厂商请求时间；新增 `total_latency_ms` 覆盖失败尝试、实际退避和厂商切换，`attempt_history` 记录每次状态、厂商、状态码、请求耗时与实际等待。最终失败也入统计；日志不打印请求、回答、密钥或异常正文。
- 缓存命中总耗时为零，缓存/回放不重复进入实时统计；旧 cassette 缺总耗时则保留 `null`，上层回退旧耗时。逻辑请求、所有实际尝试与成功单次请求分别有分位数，最近保留 500 次。失败请求没有 usage 时，无法证明厂商未计费。
- Text2SQL、RAG 重排/回答、Agent 规划/回答与 Reporter 统一使用完整耗时。业务结果保存生成记录，SQL 自修复和回答修复的计量均累计。
- 同批独立工具用 TaskGroup 执行，同一 Agent 实例跨会话共享默认三个并发额度。先按规划顺序分配 ID，完成顺序不改变引用；排队和执行时间分别记录。依赖前序结果的任务放下一轮。超时/连接取消会取消子任务并释放额度。

## 统计结果与语义约束

新增 `POST /api/ai/statistics` 与第三个只读工具 `plant_statistics`。指标来自白名单，时间显式且不超过 31 天；固定参数化 SQL 使用只读账号和 5 秒语句超时。独立统计 API 不依赖模型配置。

`kind=statistic` 中模型正文必须为空，只能选择本轮成功工具实际返回的事实 ID。完整句子、数值、单位、聚合口径、覆盖与时间由服务端提供；假 ID、失败/旧调用、同一句跨时段拼接均拒绝。告警建议也追加厂站指标的固定统计证据，保留既有 t1～t4 编号。

2026-11-06 黄官镇出水氨氮，统计时段为北京时间当日 00:00 至次日 00:00：

| 事实 | 服务端结果 |
| --- | --- |
| 5 分钟均值累计超标 | 2.5 小时，150 分钟，30 桶 |
| 已观测的最长连续超标 | 2.5 小时，30 个相邻异常桶 |
| 曾有原始采样超标的小时桶 | 4 个，不能当成连续 4 小时 |
| 原始采样瞬时最大值 | 17.3209 mg/L |
| 5 分钟均值最大值 | 16.7281 mg/L |
| 有效桶覆盖 | 288/288 |
| 按 5 分钟桶等权计算的全天平均值 | 1.7808 mg/L |
| 按上述平均值的全区降序密集排名 | 第 1 名，共 7 厂 |
| 全区上述平均值范围 | 0.4710～1.7808 mg/L |

统计只纳入已完成的 5 分钟桶，起点向上、结束点按 `min(end, now)` 向下对齐。缺失不补零且打断统计连续性；每桶至少一个非空采样即算有效，覆盖完整也不等于桶内持续观测。跨厂结论要求至少两座厂、所有厂覆盖完整且比较值齐全；按四位小数显示值比较并保留并列密集排名。

人工金标中特意覆盖“累计 35 分钟、最长连续 20 分钟、中间缺失”的样例，以及“两个小时都曾有原始超标采样、但均值异常时长为零”的样例，避免仅用这次恰好相等的 2.5 小时证明累计/连续算法。

目前固定统计覆盖厂站指标。普通文字中的已知统计句式与运行采样比例误读有护栏，但不是任意中文语义验证；设备极值和所有 Text2SQL 语义尚未全部形式化。原因分析依然是待核查假设，引用匹配不证明因果成立。

## 保留的问题发现过程

1. [首次优化复测](performance-after-stats-parallel.json)：统计把连接级 `row_factory` 改为字典行，Text2SQL 复用连接时迭代字典键，将列名当作数据。一次回答只能说明证据缺口，另一次引用校验失败，不能作为最终成功验收。修复为各自游标显式指定行格式，并用大小为一的连接池补交替调用回归。
2. [连接修复后复测](performance-after-row-factory-fix.json)：耗时降到 38.0 / 46.6 秒，但复核文字发现设备采样条数被称作运行台数。后续规划子问题明确运行采样占比或去重设备数，回答要求采样口径，并新增已知比例误读拦截；最终计时另用 `final` 标签重测。
3. [统计首轮验收](statistics-optimized.json)：三项通过，其中峰值与排名回答各修复了一次无出处的额外陈述。最终版本重新验收，三项均首轮通过。

历史文件均保留，没有以最终文件覆盖失败记录。

## 复验

在项目根目录重建 API，在 backend 执行后续脚本；每次使用新标签/新输出路径：

```bash
docker compose build api
docker compose up -d api
cd backend
uv run pytest -q
uv run python -m evals.agent.performance --label another-run --repeats 2
uv run python -m evals.agent.smoke --output evals/agent/results/api-smoke-another-run.json
uv run python -m evals.agent.statistics_smoke --label another-run
```

真实脚本会调用 Flash。固定日期问题需要保留本次模拟历史；如果重置模拟器或重新回填到另一日期，应相应调整问题与参考时段。密钥只在本地 `.env` 填写，不进入记录或报告。
