# 原始采样查数约定：验收记录（2026-11-07）

## 改动

22 题端到端诊断评测 v2 暴露了三类 Text2SQL 真实错误：

1. 用目标时刻 ±10 分钟内最近的一条代替指定时刻，并把目标时间当作采样时间返回；
2. 原始读数被 `round` 到 1 位小数，超出 0.0051 的核对容差；
3. 一题把数值转成文本。

本轮修改：

- **提示词**：按指定时刻查原始数据时要求 `ts` 精确相等，不得用相邻采样代替；返回的采样时间取读数表的实际 `ts`；原始读数不取整。
- **Few-shot**：两条示例去掉对原始读数的 `round`；新增一条按精确时刻宽表 JOIN 厂站与设备读数的示例，问题文本与两套评测均不重复。
- **评测脚本**：Text2SQL 评测新增 `--label`，同名结果存在时报错，不覆盖旧报告。

模型、数据、评分规则（`spec_sha256` 不变）均未改动；全部调用 `deepseek-flash`。

### 7 道失败题分类

另写脚本把每题参考快照的每个值，在同一采样时刻的 SQL 结果行中查找：**7 题全部参考值都能找到（共 31/31）**，失败都不是查错数。

**评分器无法追踪列来源（4 题，数值正确）：** 评分器靠解析 SQL 把结果列对回原始字段，长表 `UNION ALL` 或 `CROSS JOIN LATERAL (VALUES …)` 写法解析不了，于是报 `data_scope_or_projection` 与 `missing_snapshot_metric`。

| 题目 | 写法 |
| --- | --- |
| storm-diagnosis | CTE + 长表 UNION ALL |
| dosing-data | CTE + 长表 UNION ALL |
| dosing-followup | LATERAL VALUES |
| normal-data | LATERAL VALUES |

其中 dosing-data 的 SQL 写了 `ORDER BY (r.ts = t.ts) DESC, ABS(...) LIMIT 1`：精确时刻优先，否则取最近一条。本次碰巧拿到精确时刻，返回的也是真实采样时间，但仍不符合新约定；若该时刻缺数，会静默用相邻值代替。

**Agent 行为问题（3 题）：**

| 题目 | 失败码 | 原因 |
| --- | --- | --- |
| blower-diagnosis | `unexpected_metric` ×4、`claim_time_scope` | 题目只问 18:00 的 5 个读数，回答额外引用振动、电流、进水量、进水氨氮，并调用固定统计给出 11-06 全天超标时长，超出题目时间范围 |
| dosing-diagnosis | `required_claim_kinds` | 题目要求讨论异常可能性，回答把"待核查可能"写进核查建议，缺少 `hypothesis` 陈述 |
| pipe-diagnosis | `unexpected_metric` ×2、`data_scope_or_projection` ×4 | 额外引用进水 COD、出水氨氮；补查加药泵时对单条采样做了 GROUP BY 聚合，评分器无法对回原始值 |

## 结论与后续

- 改动目标达成：指定时刻查数不再拿相邻采样冒充，原始值不再被取整，诊断评测没有出现数值错误。
- 下一步一：评分器支持长表 UNION / LATERAL VALUES 的列追踪，或在提示词中要求原始采样查询用宽表，二选一后复测；
- 下一步二：规划阶段约束"题目已列指标时不扩展引用"，回答协议要求诊断题至少一条 `hypothesis`；
- 下一步三：12 题 needs_review 人工核查后才能报告语义通过数。

全量测试 `498 passed in 25.88s`（假模型，不调用付费 API）。

## 第二轮：评分器列追踪 + Agent 规则（同日）

### 改动

- **评分器**：按作用域逐行追踪列来源，支持 CTE、UNION 分支和 LATERAL VALUES；长表按常量列（如指标名）唯一确定分支，没有区分常量或多个分支来源不同时仍判"无法追踪"，不猜测。行能定位到正确厂站和时刻时，字符串常量（指标名、单位）按上下文放过，数值/布尔常量仍不能当证据。新增 `nearest_sample_sql`：指定时刻题出现 `ORDER BY ABS(ts - 目标)` 选点即判失败，即使碰巧命中。
- **Text2SQL**：执行前拦截同一写法，问题未要求"最接近/前后 N 分钟/最近一条采样"时退回修复（"最近 7 天"不放行）。只识别这一种已观察到的写法。
- **Agent 规划**：用户已列明指标、设备和时刻时，只查这些项；单一时刻问题不调用固定统计，除非另问时长/峰值/排名。
- **Agent 回答**：只引用用户列明的指标和时刻；诊断题有数据和知识证据时至少一条 `hypothesis`。服务端首轮强制，缺失则退回修复；修复轮仍缺时保留回答并加告警，不整轮失败（这是完整性要求，不是证据要求）。

新增测试 13 项，全量 `511 passed in 27.86s`。Text2SQL 64 题离线回放仍为 63/64，新拦截不影响这 64 题。

### 结果

| 指标 | v4 原评分 | v4 新评分器重评 | v5 `flash-agent-rules-v5` |
| --- | --- | --- | --- |
| 自动检查通过 | 15/22 | 18/22 | **21/22** |
| 失败 | 7 | 4 | 1 |
| 单题耗时中位数 / 均值 / 最大 | 8.2 / 10.4 / 30.3 秒 | — | 7.3 / 7.8 / 17.1 秒 |
| 整轮墙钟 | 3 分 49 秒 | — | 2 分 54 秒 |

- 新评分器只改判分，不改原始响应：v4 重评后 storm-diagnosis、dosing-followup、normal-data 转为待核查；dosing-data 仍失败（选点兜底，且厂站/设备编码是 SQL 常量，不是库里的值）。
- 新评分器同样重评 v2：自动检查通过仍为 10/22，但 storm-followup 由待核查改判失败（当时用了选点兜底，旧评分器没查出），另一题由失败转为待核查。新评分器在两个方向上都更准。
- v5 唯一失败 storm-diagnosis：题目只问 11 月 3 日 16:00 雨强，SQL 用 LEFT JOIN 把 11 月 2 日 16:00 的雨强（0.0 mm/h）也带出，回答引用了它。数值正确但超出题目范围，按规则判失败。
- v5 中 Text2SQL 选点拦截与"缺少原因假设"修复**均未触发**（无修复记录），提升来自提示词；服务端规则是兜底，本轮没有被实际验证到。
- 单轮结果受采样波动影响。18 题 needs_review 尚未人工核查，自动检查通过不等于诊断语义正确。
