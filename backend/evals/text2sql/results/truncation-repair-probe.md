# Text2SQL 截断修复实测（2026-11-08，deepseek-flash）

起因：Agent 实测问“高台镇昨天18点到20点好氧区DO为什么低”，规划给出的查数子问题含 DO（1#、2#）、进水流量、曝气风量、MLSS、鼓风机功率、运行占比、振动、电流等十余项，`sql_query` 超过 60 秒工具上限，整轮拒答。

方法：用同一子问题直接调用 `Text2SQL.ask`（不经 Agent、不设 60 秒上限），演示时钟 2026-11-08 16:22:35；改前单独 1 次 + 并发 3 次，改后并发 3 次（现场查数与知识检索并行，并发更接近当时情况）。

| 版本 | 次序 | 总耗时 | 每次调用（finish_reason / 输出 tokens / 耗时） | 结果 |
|---|---|---:|---|---|
| 改前 | 单独 | 12.9 s | stop / 2394 / 12.8 s | 成功，3 行 |
| 改前 | 并发 1 | 38.3 s | **length / 4000 / 25.2 s** → stop / 2647 / 12.9 s | 成功 |
| 改前 | 并发 2 | **61.4 s** | **length / 4000 / 25.2 s** → **length / 4000 / 26.1 s** → stop / 2029 / 10.0 s | 成功，但已超 60 s 工具上限 |
| 改前 | 并发 3 | 39.1 s | **length / 4000 / 24.8 s** → stop / 2667 / 14.2 s | 成功 |
| 改后 | 并发 1 | 13.1 s | stop / 2375 / 13.0 s | 成功，2 行 |
| 改后 | 并发 2 | 33.4 s | length / 4000 / 26.0 s → stop / 737 / 4.0 s（列名错）→ stop / 731 / 3.1 s | 成功，3 行 |
| 改后 | 并发 3 | 26.7 s | length / 4000 / 22.3 s → stop / 829 / 4.3 s | 成功，2 行，**漏了 2# DO** |

原因：Flash 默认思考，推理与 JSON 共用 4000 token 预算；复杂子问题常在上限处截断，正文为空。旧代码只反馈“不是合法 JSON”，修复仍开思考，容易再截断一次。

改动（`app/ai/text2sql/service.py`）：识别 `finish_reason=length`，反馈“推理过长被截断，请直接输出 JSON”，之后的修复关闭思考；累计接近 50 秒时不再修复，返回明确错误，避免被 60 秒工具上限取消。首次调用不变。

结论与限制：
- 4 条成功 SQL 重新执行后数值一致；行数差异来自“18:00至20:00”是否含 20 点一小时。
- 关思考修复每次约 3–4 秒；本次最长 33.4 s，样本仅 3 次，不能当作延迟分位数。
- 代价：关思考时 1/3 漏掉了子问题中的一项（2# DO 在小时表中无列，未改查原始表）；引用校验不会发现漏项。
- 首次调用仍可能用 20–26 秒想满预算；规划把十余项合成一条查询是根因之一，尚未调整提示词。
- 本次实测共约 7.3 万 tokens（改前 4.5 万、改后 2.8 万）。
