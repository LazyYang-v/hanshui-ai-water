# M5 视觉巡检评测报告（2026-11-08）

YOLO11n 检测两类目标：池面**漂浮物**（floating_debris）与管廊**渗漏**（leak）。ONNX 在 CPU 上推理，由 FastAPI 提供服务，检测结果按阈值合并写入告警。本报告分开给出合成数据和真实数据的指标，不合并成一个数。

## 结论

| 项目 | 结果 | 口径 |
| --- | --- | --- |
| 合成 test（300 张） | 漂浮物 AP50 0.941，渗漏 AP50 0.986；告警阈值下 34 张无目标图 0 误报 | 与训练同一生成器，**偏乐观** |
| 真实漂浮物（FloatWaste val 203 张） | 只用合成数据训练 AP50 0.229 → 加 546 张真实图 0.606 | 河道/排水沟，不是污水厂池面 |
| 渗漏真实效果 | **未知**，没有真实管廊图片 | 只能说明学会了生成器的视觉线索 |
| 导出一致性 | 同一输入张量下 PyTorch 与 ONNX 检出 586/586 一致，原始输出最大绝对误差 0.007 | 端到端差异来自预处理，见下文 |
| CPU 单张延迟（Apple M3） | 4 线程 P50 56.6 ms，1 线程 92.4 ms（含解码与前后处理） | 系统负载约 5 时测得 |
| HTTP 吞吐 | 默认 2×2 配置 16 并发约 23 rps；4×1 约 27 rps；0 错误 | 3 轮中位数，客户端与服务端同机 |

部署的是 E2（合成 + 真实），`models/vision/inspect.onnx`，sha256 `336ebeba28ef…`，与下文 pipeline 评测文件的 sha256 一致（`train.py export --deploy` 会校验，不一致则拒绝部署）。

## 数据

| 数据集 | 图片 | 漂浮物框 | 渗漏框 | 无目标图 | 用途 |
| --- | ---: | ---: | ---: | ---: | --- |
| 合成 train | 2000 | 4302 | 1168 | 200 | 训练 |
| 合成 val | 300 | 690 | 135 | 44 | 训练时选模型（两组实验都只用它） |
| 合成 test | 300 | 659 | 166 | 34 | 评测 |
| FloatWaste train 子集 | 546 | 2237 | 0 | 49 | E2 训练 |
| FloatWaste val 子集 | 203 | 787 | 0 | 5 | 评测，**不参与选模型** |

**合成数据**（`vision/synth.py`，960×540，固定种子可复现）：

- **水池场景**：曝气池、二沉池、渠道、出水口四类。漂浮物有瓶、袋、泡沫团、树枝、易拉罐、杯、容器 7 种形态。
- **不标注的干扰物**：波纹、泡沫区、气泡、浮渣、反光、落叶、栏杆、远墙、近处走道，用来教模型"这些不是漂浮物"。
- **管廊场景**：渗漏有水痕、积水、水痕 + 积水、湿斑四种形态，通过压暗、边缘加深、积水平滑和灯光反射渲染。
- **管廊难负样本**：锈迹、污渍、干痕、油漆、投影、地面反光、管道阴影。
- **相机效果**：亮度、对比度、色偏、暗角、12% 红外灰度、模糊、噪声、40% 叠加时间水印、JPEG 质量 55–95。

**真实数据**：[FloatWaste](https://huggingface.co/datasets/OliviaWuYJ/sc-floatwaste)（CC BY 4.0，DOI 10.5281/zenodo.21934286），处理方式如下：

- 按地区分层抽样，长边缩到 1280 后转 JPEG，25 个类别合并为 floating_debris。
- 尺寸与标注不符的图片先按 EXIF 旋转，仍不符就丢弃；所有负样本都保留。
- 使用数据集自带的 train/val 划分。
- 受下载带宽限制（约 300 KB/s），子集缩小为 train 500 张 + val 200 张的目标（负样本另计），地区比例调为 Hobart 0.40 / NSW 0.32 / Indonesia 0.28。
- 实际分布：train Hobart 246、NSW 160、Indonesia 140；val Hobart 83、NSW 64、Indonesia 56。

## 训练

两组实验用同一个起点（Ultralytics yolo11n.pt，COCO 预训练）和同样的超参：

- 输入 640，batch 16，20 个 epoch，最后 5 个 epoch 关闭 mosaic，种子 0。
- 用 MPS（Apple M3、24 GB）训练。

| 实验 | 训练数据 | 用时 | 合成 val mAP50 / mAP50-95（最后 epoch） |
| --- | --- | ---: | --- |
| E1 synth | 合成 train | 105 分钟 | 0.969 / 0.836 |
| E2 mixed | 合成 train + FloatWaste train | 114 分钟 | 0.962 / 0.831 |

训练期间同机还运行着其他项目的容器，负载均值常在 30～50，用时只作参考。

## 精度

主口径是**部署链路**（`evals.vision.run pipeline`）：直接调用 `app/vision/detector.py`，即线上实际运行的 Pillow 解码、letterbox、onnxruntime、numpy NMS 这套代码。AP 按 COCO 101 点插值计算，置信度下限 0.001。P/R 在告警阈值下统计：漂浮物 0.45、渗漏 0.50。

| 集合 | 类别 | 实验 | AP50 | AP50-95 | 告警阈值 P | 告警阈值 R |
| --- | --- | --- | ---: | ---: | ---: | ---: |
| 合成 test | 漂浮物（659 框） | E1 | 0.943 | 0.771 | 0.987 | 0.901 |
| | | E2 | 0.941 | 0.759 | 0.988 | 0.886 |
| 合成 test | 渗漏（166 框） | E1 | 0.986 | 0.903 | 0.988 | 0.952 |
| | | E2 | 0.986 | 0.898 | 0.976 | 0.964 |
| 真实 val | 漂浮物（787 框） | E1 | 0.229 | 0.140 | 0.341 | 0.342 |
| | | E2 | **0.606** | **0.392** | 0.795 | 0.482 |

Ultralytics 自带 val（OpenCV 缩放、NMS IoU 0.6）的交叉核对结果，与上表差别在 0.02 以内：

| 实验 | 合成 test mAP50 | 真实 val mAP50 |
| --- | ---: | ---: |
| E1 | 0.968 | 0.215 |
| E2 | 0.967 | 0.599 |

**图片级结果（告警视角）**：

- **合成 test**：两组实验在 34 张无目标图上都是 0 张告警。按场景和干扰物切片（波纹、反光、锈迹、管道阴影、地面反光等 16 类），各切片也都是 0 误报，但每片只有 4～20 张，只能说明没有明显被骗到的类别。
- **真实 val**：E1 有目标图的命中率为 0.93，高于 E2 的 0.81，但 E1 的框精度只有 0.34，命中多半靠误检凑出来，不能当作优点。真实 val 只有 5 张无目标图（E1 5/5、E2 2/5 触发），样本太少，**不报告真实误报率**。
- **渗漏误报**：真实 val 上两组实验都是 0 张图触发渗漏告警。河道图片里没有管廊，这只说明没有把水面误判成渗漏。

## 域差分析

按目标尺寸和地区拆开真实 val 的召回（告警阈值 0.45、IoU 0.5）。尺寸用目标在模型 640 输入里的 √面积衡量：

| 目标尺寸 | 标注框 | E1 召回 | E2 召回 |
| --- | ---: | ---: | ---: |
| <16 px | 357（45%） | 0.171 | 0.224 |
| 16–32 px | 262 | 0.504 | 0.645 |
| 32–64 px | 125 | 0.464 | 0.752 |
| ≥64 px | 43 | 0.419 | 0.837 |

| 地区 | 标注框 | E1 P / R | E2 P / R |
| --- | ---: | --- | --- |
| Hobart | 219 | 0.355 / 0.580 | 0.831 / 0.694 |
| NSW | 80 | 0.223 / 0.563 | 0.911 / 0.638 |
| Indonesia | 488 | 0.424 / 0.199 | 0.740 / 0.361 |

1. **合成数据没有教会"真实漂浮物长什么样"。** E1 对大目标（≥64 px）的召回只有 0.42，比中等目标还低：生成器画的瓶、袋、泡沫团在真实大尺寸下不像真东西。加入真实图后升到 0.84，是提升最大的一档。精度从 0.34 升到 0.80，说明 E1 还把大量真实水面纹理误当成了漂浮物。
2. **剩下的主要缺口是小目标。** 45% 的真实标注在模型输入里不足 16 px，E2 对这部分的召回只有 0.22。原因是 1280 宽的原图缩到 640 后细碎漂浮物只剩几个像素，而合成数据的目标普遍更大。可选改进：提高输入分辨率或切片推理，代价是延迟成倍增加；或者在合成数据里加入更小、更密的目标。
3. **地区差异主要是尺寸分布不同。** Indonesia 占真实标注的 62%，多是密集的细碎垃圾，召回只有 0.36；内置样例里的失败案例 `real_indonesia_00057.jpg` 就是这一类（天空倒影 + 大量细碎漂浮物，只检出 2 个低于告警阈值的框）。
4. **对上线的意义**：厂内池面的摄像头视角、目标大小和干扰物与河道不同。上线前需要采集厂内图片、标注一个验证集，再决定阈值和是否需要切片推理。

## 导出一致性（`evals.vision.run parity`，每个集合 100 张）

| 层次 | 集合 | ONNX 检出 | 参照检出 | IoU≥0.9 匹配率 | 分数差 P95 / 最大 |
| --- | --- | ---: | ---: | ---: | --- |
| 同一张量 | 合成 test | 291 | PyTorch 291 | 100% | 0 / 0（4 位小数） |
| 同一张量 | 真实 val | 295 | PyTorch 295 | 100% | 0 / 0 |
| 端到端 | 合成 test | 291 | Ultralytics 290 | 98.6% | 0.049 / 0.067 |
| 端到端 | 真实 val | 295 | Ultralytics 276 | 89.1% | 0.155 / 0.236 |

第一次对照只做了端到端比较，真实图上出现 0.236 的分数差，最初怀疑导出有问题。拆成两层后确认，导出本身是一致的，差异来自预处理：

- **输入形状不同**：Ultralytics 对 `.pt` 模型推理时按步长取最小填充，16:9 的图输入 640×384；部署的静态 ONNX 用 640×640。
- **缩放算法不同**：部署链路用 Pillow 双线性缩小，带抗锯齿；OpenCV 的 INTER_LINEAR 不带。真实图要从 1280 缩到 640，影响比合成图（960 缩到 640）更大。

部署链路的精度以上一节的 pipeline 评测为准：真实 val AP50 0.606，不低于 Ultralytics val 的 0.599，说明这些预处理差异没有让部署链路变差。

## 延迟与吞吐

**进程内单张延迟**（`evals.vision.run latency`，每档 200 次，预热 10 次，单位 ms，P50 / P95）：

| 图片 | 算子线程 | 解码 | 预处理 | 推理 | 后处理 | 合计 |
| --- | ---: | --- | --- | --- | --- | --- |
| 960×540 合成 | 1 | 2.0 / 2.1 | 3.2 / 3.4 | 87.0 / 90.9 | 0.3 / 0.3 | 92.4 / 96.4 |
| | 2 | 2.6 / 4.2 | 4.2 / 6.9 | 60.8 / 99.0 | 0.4 / 0.6 | 67.6 / 111.0 |
| | 4 | 3.1 / 5.1 | 5.2 / 9.7 | 47.0 / 79.6 | 0.4 / 0.7 | 56.6 / 95.1 |
| 1280×720 真实 | 1 | 5.2 / 6.2 | 5.7 / 6.3 | 88.5 / 98.5 | 0.3 / 0.4 | 100.0 / 111.9 |
| | 4 | 8.0 / 10.8 | 8.5 / 9.9 | 41.2 / 63.1 | 0.5 / 0.7 | 58.5 / 82.0 |

**HTTP 压测**（`evals.vision.run http`）：

- 每档 200 个请求，`alarm=false`。仍会写巡检记录，所以服务连的是独立测试库 `shuiwu_test`，不污染演示库。
- 三种服务端配置交替各跑 3 轮，下表取中位数，括号内为 3 轮范围。
- 服务端并发 × 算子线程由 `VISION_CONCURRENCY` / `VISION_THREADS` 设置。

| 服务端配置 | 客户端并发 | 延迟 P50 (ms) | 延迟 P95 (ms) | 吞吐 (rps) | 服务端排队 P50 (ms) |
| --- | ---: | --- | --- | --- | ---: |
| 2×2（默认） | 1 | 58.9（58.6–65.5） | 72.5 | 15.1（15.0–16.7） | 0 |
| | 4 | 166.7 | 201.7 | 23.3（14.4–26.2） | 71 |
| | 16 | 680.3 | 760.3 | 22.9（16.8–23.5） | 581 |
| 4×1 | 1 | 101.2 | 106.6 | 9.8 | 0 |
| | 4 | 125.6 | 151.6 | 31.0（20.3–32.1） | 0 |
| | 16 | 581.7 | 680.9 | 26.7（24.6–28.4） | 413 |
| 1×4 | 1 | 48.5（46.4–49.0） | 60.6 | 19.6 | 0 |
| | 4 | 180.9 | 251.8 | 20.9 | 120 |
| | 16 | 748.3 | 873.5 | 20.2（20.2–21.0） | 686 |

- **为什么默认用 2×2**：单请求延迟接近 1×4，吞吐介于两者之间。摄像头多、按吞吐计费时可改成 4×1，吞吐约 +17%，单请求延迟约翻倍。所有轮次 0 错误。
- **吞吐上限从哪来**：客户端并发超过服务端并发后，新增延迟几乎都是排队（`timings_ms.queue` 单独计时）。吞吐上限由 CPU 决定，与 HTTP 层无关。
- **测量噪声**：同一配置单轮最多相差约 40%（2×2 首轮 16 并发 16.8 rps，后两轮约 23 rps）。原因有三：同机 Docker 虚拟机长期占用约 3 核，训练后有约 10 GB swap 在换回，压测客户端与服务端同机。另外，进程内 4 线程测得 56.6 ms，HTTP 1×4 单请求的服务端合计只有 37.8 ms，两次测量的时刻不同，这个差距本身也是噪声的一部分。所以这里只做配置之间的相对比较；绝对值要在空载或独立机器上重测。
- 原始结果：`latency-*.json`、`http-*.json`，每个文件都记录了测量前后的负载。

## 告警运行点

- **阈值与滞回**：
  - 漂浮物：置信度 ≥0.45 开告警，<0.25 才算恢复；同一画面 ≥3 个目标升级为预警。
  - 渗漏：阈值 0.50 / 0.30，一律按预警处理。
- **事件合并**：
  - 同一厂站、同一摄像头、同一类别的检测合并为一个事件，30 分钟不再出现即视为旧事件。
  - 人工关闭的事件不再合并，之后的检测会开新事件。
- **数字边界**：上文合成集的 0 误报是在这组阈值下测得的；真实集上漂浮物精度 0.795，即约每 5 个告警级框中有 1 个是误检。

## 局限

1. **渗漏只有合成数据。** 真实管廊里的渗漏可能更细、更暗，背景也更复杂，模型效果未知。上线前需要采集厂内图片并标注。
2. **真实漂浮物验证用的是河道/排水沟图片**，污水厂池面（曝气泡沫、浮渣、池壁）与之不同；本报告的真实 AP 不能代表厂内效果。
3. **合成 test 与训练集出自同一生成器**，高分只说明模型学会了生成器定义的视觉线索。
4. **真实 val 只有 5 张负样本**，不能估计真实误报率；子集的地区比例因带宽调整过，与原数据集分布不同。
5. **只训练了 20 个 epoch、单个种子**，没有做种子方差和更大模型的对比。

## 复现

```bash
cd backend
uv run --group vision python vision/synth.py                       # 合成数据 → data/vision/synth
uv run python -I vision/floatwaste.py --workers 10                 # FloatWaste 子集（可断点续传）
uv run --group vision python vision/train.py train --exp e1_synth
uv run --group vision python vision/train.py train --exp e2_mixed
uv run --group vision python vision/train.py export --exp e2_mixed            # → runs/e2_mixed/weights/best.onnx
uv run python -m evals.vision.run pipeline --model data/vision/runs/e2_mixed/weights/best.onnx --label e2_mixed
uv run --group vision python vision/train.py export --exp e2_mixed --deploy   # 校验 sha 后复制到 models/vision/
uv run --group vision python -m evals.vision.run parity --n 100 --label e2_mixed
uv run python vision/samples.py                                    # 内置样例
uv run python -m evals.vision.run latency --label e2_mixed --image models/vision/samples/synth_aeration.jpg
uv run python -m evals.vision.run http --label e2_mixed-c2t2 --image models/vision/samples/synth_aeration.jpg
```
