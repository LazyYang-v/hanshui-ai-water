# LLM 网关并发压测报告

2026-11-08，MacBook（Apple M3，8 核），压测端与假厂商同机。由 `evals/gateway/load.py` 生成原始数据：

- `fake-before.json`：改动前的网关（同一脚本，替换成改动前的 `app/ai/gateway.py` 源码运行；该版本未入库）
- `fake-after.json`：改动后的网关
- `live-*.json`：真实 DeepSeek Flash（见第 5 节）

```bash
uv run python -m evals.gateway.load fake --label after
uv run python -m evals.gateway.load live --label flash --n 100 --concurrency 50   # 产生费用，只允许 deepseek-flash
```

## 1. 方法

假厂商（`evals/gateway/fake_provider.py`）是独立进程的 OpenAI 兼容服务，行为可配置：延迟（对数正态）、逐 token 流式、同时处理上限（超出返回 429，可带 Retry-After）、随机 503。压测走真实的 httpx 连接池与本机网络栈，不是进程内 mock。

- 非流式响应里带假厂商实际处理时间 `server_ms`，用「客户端总耗时 − server_ms」得到网关 + HTTP 开销；流式首个 chunk 带 `server_ttft_ms`，同理得到首字开销。
- 每个请求的消息不同，`use_cache=False`，不命中网关缓存。
- 每次厂商尝试按 `厂商:状态码/异常类型` 计数（`attempt_outcomes`），失败请求的尝试也计入。
- 对照组「裸 httpx」：同样配置的 AsyncClient 直接请求假厂商。

### 测量陷阱：本机代理

本机设置了 `HTTP_PROXY=http://127.0.0.1:7897`，httpx 默认读取，**连 127.0.0.1 的请求也经过代理**。最初一轮压测因此出现两个假象：

1. 并发 100 时约 1% 请求得到代理返回的空 502（无 body、无 content-type），网关和裸 httpx 都有；当时看上去像网关在高并发下出错。
2. 「网关开销」里混入了代理转发时间。

现在 `run_fake` 会把 127.0.0.1、localhost 设为不走代理，结果 JSON 的 `machine` 字段记录代理环境变量。下面所有数字都是绕过代理后测的，最初那轮数据已删除。真实 Flash 压测是否经过代理会单独标注。

## 2. 改了什么

| 问题（改动前） | 改动 |
|---|---|
| 429 与 503 一样计入熔断：连续 3 次 429 就熔断整个厂商，所有后续请求直接失败 | 429 是限流背压，不计入熔断，照常按 Retry-After 重试；Retry-After 支持小数秒，超过 10 秒不在本厂商等待、直接降级 |
| 网关不限制对厂商的在途请求数，突发流量直接变成 429 | 每个厂商可配并发上限（`LLM_MAX_CONCURRENCY`，默认不限），超出在网关内排队；`AttemptRecord.queue_ms` 与统计里的 `queue_p50/p95_ms` 记录排队时间 |
| 「连续失败 3 次」熔断：30% 错误率下很快连续 3 次失败，主厂商被切走 | 按失败率熔断：最近 50 次尝试里至少 20 次，且「失败 /（已完成 + 在途）」≥ 50% 才熔断。分母含在途请求，见下文 |
| 退避等待期间其他请求已把厂商熔断，等完仍会再打一次故障厂商 | 退避结束后重新检查熔断，已熔断就直接降级 |

为什么分母要算在途请求：高并发下失败（立即返回的 503）比成功（要等完整生成）先回来。第一版只看已完成的尝试，30% 错误率的场景里，前 500 ms 窗口内几乎全是失败，失败率被时间偏差抬到 100%，仍然误熔断（264/300 请求被切到更慢的备用厂商）。改为把在途请求当作「可能成功」计入分母后，只有「即使在途全部成功、失败率仍过半」才熔断。真正的故障（全部 503 或全部超时）不受影响。

## 3. 结果（改动前 → 改动后）

### 3.1 网关自身开销

固定 500 ms 厂商延迟。表中是开销 = 客户端耗时 − 厂商处理时间，单位 ms，p50 / p95。

| 并发 | 请求数 | 改动后：网关 | 改动后：裸 httpx | 改动前：网关 | 吞吐（改动后网关） |
|---|---|---|---|---|---|
| 1 | 40 | 3.1 / 4.8 | 3.0 / 3.9 | 2.8 / 10.4 | 2.0 rps |
| 10 | 500 | 5.3 / 12.9 | 4.8 / 15.8 | 4.2 / 12.7 | 19.7 rps |
| 50 | 500 | 33.0 / 53.7 | 32.8 / 54.8 | 25.7 / 55.5 | 92.4 rps |
| 100 | 500 | 53.6 / 68.8 | 50.6 / 70.4 | 63.0 / 70.2 | 176.1 rps |

各档并发下网关与裸 httpx 的开销都在测量波动范围内：网关逻辑（重试判断、统计、熔断）的开销可以忽略。并发 50/100 时几十毫秒的开销来自同机的单进程假厂商与本机网络栈，裸 httpx 一样。全部 0 失败。

### 3.2 限流：厂商同时最多处理 20 个，客户端并发 50，300 个请求

| 配置 | 成功率 | 打到厂商的请求 / 其中 429 | 延迟 p50 / p95（成功请求） | 吞吐 |
|---|---|---|---|---|
| 改动前，Retry-After: 1 | **7.3%** | 52 / 30 | 525 / 1660 ms | 176.5 rps（大多是快速失败） |
| 改动前，无 Retry-After | 7.3% | 52 / 30 | 521 / 1053 ms | — |
| 改动后，Retry-After: 1 | 81.3% | 462 / 218 | 511 / 2589 ms | 41.7 rps |
| 改动后，无 Retry-After | 74.0% | 501 / 279 | 510 / 2041 ms | 45.5 rps |
| 改动后，并发上限 20 | **100%** | 300 / 0 | 1051 / 1537 ms | 39.2 rps |
| 改动后，并发上限 16 | 100% | 300 / 0 | 1529 / 1984 ms | 30.7 rps |

- 改动前，前 3 个 429 就把唯一的厂商熔断，278 个请求直接得到「所有厂商均不可用」。
- 只修熔断不加并发上限：成功率回到约 80%，剩下的请求重试 2 次仍然碰上 429。继续加大重试次数只会让 429 更多。
- 并发上限等于厂商容量时，429 为 0，吞吐 39.2 rps，接近理论上限 20 / 0.5 s = 40 rps；延迟里的排队部分 p95 约 1.0 s，是厂商容量不够的真实代价，被显式计量（`queue_ms`），不再表现为失败。上限设小了（16）吞吐按比例下降。
- 结论：厂商有已知并发配额时，应把 `LLM_MAX_CONCURRENCY` 设为配额。DeepSeek 不公布固定并发上限、高负载时以变慢为主，所以默认不限，429 交给重试处理。

### 3.3 降级：主厂商 30% 随机 503（500 ms），备用 800 ms，并发 50，300 个请求

| | 成功率 | 主 / 备用承接 | 延迟 p50 / p95 | 主厂商熔断 |
|---|---|---|---|---|
| 改动前 | 100% | 43 / 257 | 826 / 838 ms | 3 次连续失败后打开 |
| 改动后（只看已完成尝试，中间版本） | 100% | 36 / 264 | 825 / 842 ms | 仍被时间偏差误触发 |
| 改动后（分母含在途） | 100% | **284 / 16** | **523** / 1456 ms | 未打开 |

改动后 95% 的请求留在更快的主厂商，p50 从 826 ms 降到 523 ms。代价是 p95 变高：约 30% 的请求要重试 1～3 次，每次加 0.2/0.4 s 退避。只有 16 个请求 3 次都失败，才降级到备用厂商。

### 3.4 故障：主厂商不可用、备用正常（500 ms），并发 50，300 个请求

| 故障 | 改动前 p50 / p95 / max | 改动后 p50 / p95 / max | 打到主厂商的尝试（前 → 后） |
|---|---|---|---|
| 立即返回 503 | 523 / 551 / 756 ms | 526 / 748 / 767 ms | 52 → 50 |
| 不响应，2 s 读超时 | 533 / 2584 / **4755** ms | 522 / 2735 / **2757** ms | 52 → 50 |

- 两版都 100% 成功，都只在第一波请求时打到故障厂商，熔断后全部直接走备用。
- hang 场景的最长耗时从 4.8 s 降到 2.8 s：改动前，退避期间熔断已打开，有请求仍会再等一次 2 s 超时。p95 约 2.7 s，是第一波请求（50/300，约 17%）各等一次读超时、再加备用的 0.5 s，下限由超时设置决定。生产环境的超时是 `LLM_TIMEOUT_S=60`，真实宕机时第一波请求会等更久。
- 立即 503 的 p95 比改动前高约 200 ms，这是最少 20 次尝试才判定熔断的代价：第一波请求在熔断前多退避重试一次。换来的是 3.3 节里不会被 30% 错误率误熔断。
- 不再用「连接一个没有监听的端口」模拟宕机：macOS 对关闭端口回 RST 有限速，单次连接要 2～4 s，测的是操作系统而不是网关。

### 3.5 流式首字延迟

假厂商首字延迟中位数 400 ms（对数正态 σ=0.3），之后 100 个 token、每 20 ms 一个。

| 并发 | 请求数 | 首字 p50 / p95 | 网关首字开销 p50 / p95 |
|---|---|---|---|
| 1 | 30 | 395 / 775 ms | 2.8 / 6.2 ms |
| 50 | 300 | 396 / 657 ms | 3.7 / 13.6 ms |

并发 50 时网关首字开销 p95 为 13.6 ms，首字延迟基本就是厂商本身的首字延迟。（并发 1 只有 30 个样本，p95 是样本里的极值，受 σ=0.3 的随机延迟支配。）

## 4. 结论

- 网关在并发 100 以内不是瓶颈：开销与裸 httpx 一致，流式首字额外开销 p95 < 15 ms。
- 改动前的熔断在两种常见情况下帮倒忙：限流时把唯一厂商熔断（成功率 7.3%），30% 错误率时过早切走主厂商。改为「429 不计入 + 按失败率熔断 + 分母含在途」后，两种情况都恢复正常，真实故障时的熔断速度基本不变。
- 厂商有固定并发配额时，网关侧并发上限比重试更有效：限流场景中成功率从 81% 到 100%，429 从 218 降到 0。

局限：压测端与假厂商同机，绝对开销含本机网络栈和单进程假厂商的排队。假厂商的限流是「超过容量立即 429」，真实厂商可能是令牌桶或排队变慢。故障场景只覆盖单厂商完全不可用，没有覆盖半故障（如 30% 超时）。熔断没有半开状态，冷却结束后流量全部放回，再按窗口重新判断。

## 5. 真实 DeepSeek Flash

2026-11-08 04:48，`deepseek-flash`，提示词「用一句话（不超过40字）说明污水处理厂曝气池溶解氧偏低可能的一个原因。编号{i}。」（编号不同，避免命中厂商侧缓存），temperature 0.3，max_tokens 120，关闭思考。先跑流式 100 次，再跑非流式 100 次，客户端并发 50。网关不设并发上限。请求经过本机 HTTP 代理（`proxy_env` 已记录），延迟包含代理转发与公网往返。结果文件：`live-flash.json`。

| | 成功 | 结束原因 | 首字 p50 / p95 / max | 总耗时 p50 / p95 / max | 墙钟 | tokens（输入 / 输出） |
|---|---|---|---|---|---|---|
| 流式 | 100/100 | stop 100 | **928 / 1539** / 1879 ms | 1329 / 2041 / 4055 ms | 4.1 s | 2700 / 2245 |
| 非流式（业务实际用法） | 100/100 | stop 100 | — | 1290 / 1632 / 2115 ms | 3.2 s | 2800 / 2430 |

- 没有 429、没有重试，熔断未触发。DeepSeek 在并发 50 下没有限流，主要表现是延迟波动。
- 首字 p95 约 1.5 s，比 p50 高约 66%。结合 3.5 节，网关自身的首字开销 p95 不到 15 ms，这部分波动来自厂商和网络。
- 只有 100 个样本，p95 是第 95 名附近的值，p99/max 只有 1～5 个样本，只作参考。这是一次性测量，没有跨时段重复，不代表 DeepSeek 在高峰时段的表现。

### 5.1 第一轮作废：思考模式吃掉了输出预算

第一轮（`live-flash-thinking-default.json`）没有显式关闭思考，其余设置相同：

- 200 次全部成功，但流式只有 22/100 次输出了正文；非流式 completion tokens 合计 12000，正好等于 100 × max_tokens。
- 关闭思考后同一设置 200 次全部正常结束（stop），输出 tokens 降到约 1/5，可以确认第一轮是 Flash 默认开启思考，120 token 在推理阶段就用完了，没有输出正文就被截断。
- 网关的首字延迟只统计正文，所以第一轮的首字 p50 2.9 s 只有 22 个有偏样本（推理较短的那些），不能作为首字延迟。

为此，网关的 `stream()` 增加了与 `chat()` 一致的 `thinking` 开关。压测脚本记录每次的 `finish_reason` 和「正文为空」，并保存 3 条回答样例。两轮共计约 4.5 万 token，全部是 Flash。业务侧仍按各模块原有的思考设置：Text2SQL、RAG 与首轮规划保持默认，Agent 综合回答与第二轮规划关闭思考。
