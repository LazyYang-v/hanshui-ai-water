# 因果告警扫描与进水污染负荷预警验收

日期：2026-11-07。本轮完成两项：统一生产巡检与评测的历史可见性、扫描合并/恢复流程；增加进水 COD、总氮和氨氮质量负荷预警。运行数据全部来自模拟器或明确构造的回归样本，本轮没有调用大模型。已重建本地 API，健康检查正常，当前只配置 DeepSeek Flash。

## 实现

旧生产扫描以扫描结束时的近 7 天数据拟合一份基线，再反推窗口内所有历史；旧评测则冻结评测开始前的基线，并在内存另写持久化流程。两者不一致。现在 `SignalHistory.window` 对每个判断桶使用其所在整点之前 7 天的完整小时；当前小时与未来小时均不可进入该桶的基线。进水中位数、药耗模型和新增负荷基线遵循同一口径。过去异常仍可能进入后续历史，由中位数/MAD或稳健拟合压低影响，不根据场景标签删样本。

主评测每 5 分钟推进演示时钟，实际调用生产 `scan → detect → persist/plan` 写入独立 `shuiwu_alarm_eval.alarm`。预载只读 SQL 聚合省掉重复原始取数，切窗、逐时基线、检测、事务合并与生产相同；每种子在 6 个时刻逐字段对照直接 SQL 路径。数据库聚合顺序可能带来约 1e-15 浮点尾差，对照容差为 1e-9。

小时基线直接查询原始数据，迟到数据不必等连续聚合刷新。新事件保存 `condition_confirmed_at` 和 `detected_at`：前者是数够有效异常桶后的数据时刻，后者是实际首次发现的扫描时刻。检出延迟取后者，包含停机补扫等待。

扫描起点前移到最早未恢复事件，超过 7 天也不截断；删除按“设备/厂站已有后续数据覆盖”推断恢复的兜底。恢复必须由本规则数够有效正常桶。缺失或暂停评估不算正常，也不中断既有有效计数。数据恢复 `ended_at` 与人工处理 `status` 仍独立。

## 新负荷规则

同一采样的 `inflow_m3h × 浓度 ÷ 1000` 先计算 kg/h，再取 5 分钟均值；这与流量均值乘浓度均值不同。回归样本 `(100m³/h,1000mg/L)`、`(1000m³/h,100mg/L)` 的正确负荷均值为 **100kg/h**，均值相乘会错成 **302.5kg/h**。

- 派生指标为 `cod_load_kgh`、`tn_load_kgh`、`nh3n_load_kgh`，在独立目录及 `/api/metrics.derived` 展示；原始浓度仍为 mg/L，派生键不进入原始 SQL 列白名单。
- 取前 7 天同一北京时间钟点至少 3 个完整小时，负荷需超过 `max(中位数×1.5, 中位数+3×1.4826×MAD)`，浓度需超过 `max(中位数×1.25, 中位数+3×1.4826×MAD)`。
- 连续 3 个有效异常桶确认，3 个有效正常桶恢复。事件触发值、关注阈值与最不利值均为 kg/h，细节保留浓度、流量、基线、倍率、拟合时点及模式。
- 单纯增水稀释不触发浓度型负荷冲击；水量与浓度都上升时仍预警并注明，不能仅凭该告警认定上游偷排或出水已超标。
- 告警建议通过专用 SQL 先算 5 分钟负荷，再压缩展示浓度、流量、出水与 DO/风量背景；不会把浓度统计改标为 kg/h。工单模板增加负荷核算、仪表复核、取样及上游来源核查，仍须用户确认才写工单。

## 最终回放

每种子先生成 7 天历史，再生成 6 天评测：8 个异常场景、1 场阴性小雨，最后一天无事件。中间停机 6 小时；每组实际完成 1656 次扫描。

| 步长/种子 | 异常场景检出 | 误报/厂站·天 | 全量/增量事件 | 缺失/多出/字段差异 | 恢复判定改写 | 雨期负荷伴随事件 |
| --- | --- | --- | --- | --- | --- | --- |
| 60秒/1 | 8/8 | 0/42 | 43/43 | 0/0/0 | 0 | 2 |
| 60秒/2 | 8/8 | 0/42 | 39/39 | 0/0/0 | 0 | 1 |
| 60秒/3，保留验证 | 8/8 | 0/42 | 38/38 | 0/0/0 | 0 | 0 |
| 5秒/1 | 8/8 | 0/42 | 37/37 | 0/0/0 | 0 | 0 |

字段对照包含恢复时间、级别、最不利值及出现时间。`alarm.peak` 为 REAL，最终表值与纯函数四位小数峰值以 0.001 容差比较，其余字段精确比较。按时采样主评测的全量与增量一致；迟到情形另用实际写入顺序验证。

60秒三种子共 **24/24**，126厂站·天按场景归因误报为0；5秒种子1为 **8/8**、42厂站·天误报为0。归因窗口为场景开始至结束后6小时，同厂预期规则算命中、其他规则算伴随，窗口外及阴性样本算误报。该口径有较宽的伴随窗口，**零误报不等于真实业务精确率**。三个相关污染物可产生多条事件，也可能回落后重触发，不能拿事件数当独立场景数。

### 参数选择与雨期事件

仅在60秒种子1/2比较负荷倍率1.4/1.5/1.6与持续2/3/4桶，种子3用于保留验证。浓度1.25倍与3倍稳健标准差保持固定；候选使用相同因果基线和状态机，候选延迟为条件确认时间，不含停机等待。

| 持续桶 | 两种子冲击检出 | 延迟 | 窗口外/阴性误报 | 雨期负荷事件，两种子合计 |
| --- | --- | --- | --- | --- |
| 2 | 4/4 | 10分钟 | 0 | 4 |
| 3 | 4/4 | 15分钟 | 0 | 3 |
| 4 | 4/4 | 20分钟 | 0 | 2 |

三个负荷倍率在本样本上结果相同，无法证明其中一个最优。默认1.5倍和3桶是灵敏度、15分钟确认及短暂波动之间的折中，不能宣称完成真实厂站阈值标定。

默认60秒回放的3条雨期负荷伴随事件分别是种子1 P07总氮/氨氮、种子2 P04氨氮。触发时负荷为历史中位数的 **1.56–1.74倍**，浓度约 **1.27–1.30倍**，不是只有水量增加、浓度下降的稀释。模拟器包含雨天初期冲刷；这些事件保留并单列，未当作独立工业污染命中，也未计入窗口外/阴性误报。5秒复核没有这类雨期负荷事件；纯稀释构造回归也没有触发。

## 验证与部署

- 完整自动测试：**412 passed in 27.76s**，含真实独立测试库集成，无跳过，模型为假响应。最后仅调整负荷模式元数据后，相关 **52 passed in 6.00s**。
- 六类真实SQL写入时序检查：缺失不恢复、6小时停机后补扫、迟到数据保留实际发现时刻、未来采样不可见、9天未恢复保持开放、随后有效正常值确认恢复。每组均通过。
- 独立真实 Uvicorn/HTTP：**9/9**，实际请求 `/api/alarms/scan`、指标目录、告警列表、草稿与工单列表，三项负荷值/单位正确、三桶正常后恢复、重复扫描无新增更新；正式工单数0。该服务使用独立 `shuiwu_alarm_smoke` 库及进程内Redis，退出时关闭，无模型调用。
- 本地8000端口API已重建；DB、Redis、模拟器健康，9类规则已注册，手动扫描成功且无重复新增，巡检无错误。一次含原始取数的扫描约222ms，仅作运行快照，不作为性能分位数。当前唯一启用模型为`deepseek-flash`，本轮模型调用数0，演示库工单数0。

回放扫描计时包括真实告警表读取和写入，但使用预载聚合，不含每轮原始数据聚合；不能直接当线上扫描耗时。最终60秒三组中位数44.1/28.4/20.7ms，5秒为19.3ms；机器上并行任务影响耗时，不据此作提速结论。

在backend目录执行，每次换新标签；不要并发重建同一评测库：

```bash
uv run pytest -q
uv run python -m evals.alarms.run --label another-60s --seeds 3 --step 60 --tune
uv run python -m evals.alarms.run --label another-5s --seeds 1 --step 5

```

## 边界

正常巡检只补最近3小时，超窗迟到需手动补扫，初次启动补扫仍为7天；已有开放事件会延长窗口。主回放按时间前缀模拟按时采样可见性，迟到另按真实写入顺序验证。原始表没有完整的采集/到达双时间轴，事后仅凭最终数据不能复原任意历史上报序列。

长事件依赖原始历史留存，完整重放会增加开销。持续异常可能进入后续基线并改变阈值，稳健统计不保证能隔离长期污染。规则关注浓度型冲击；稀释条件下的高水量风险仍需独立大流量规则与现场判断。60秒与5秒噪声的相关时间不同，分别报告。既有告警不重置、不补造旧版缺失的首次发现时刻。所有结果仅说明本模拟器和指定回归样本上的表现，不是实际水厂检出率或收益。
