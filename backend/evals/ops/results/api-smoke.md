## 处置建议

请求：`POST /api/alarms/15/advice`。对象是 P06 黄官镇污水处理站 11-06 的出水氨氮超标事件，按 5 分钟均值于 15:45 开始、18:15 恢复，最不利值约 16.73 mg/L。

| 检查项 | 结果 |
| --- | --- |
| HTTP / 结果 | 200，`ok=true`、`saved=true`、`refused=false` |
| 实际模型 | `deepseek-flash` |
| HTTP 耗时 | 约 5.1 秒（手动联调记录） |
| 建议生成耗时 | `total_ms=4952.9`；仅建议综合步骤，不含此前取证 |
| 模型耗时 | `llm_ms=4947.1` |
| Token | 输入 4133 + 输出 902 |
| 陈述 | 事实 3、待核查假设 1、核查建议 1 |
| 引用 | 17 处：数据 13、知识 4 |
| 校验 | 首轮通过，`validation_errors=[]` |

证据由服务端固定查询，不经过 Text2SQL 或 Agent 规划：

- `t1`：14:45–18:45 的 15 分钟工艺表，16 行，含氨氮、总氮、DO、风量、进水与 MLSS。
- `t2`：告警开始前后 6 小时内同厂其他告警，7 行。
- `t3`：鼓风机汇总，2 行，含非备用机和备用机的运行占比、振动、温度。
- `t4`：混合检索返回 4 个知识片段，此路径未调用 Flash 重排。

回答按时间描述停机、风量下降、DO 偏低和氨氮滞后升高，原因保留为供氧不足的待核查假设。引用单元格和知识摘录可在原始响应中复核，原因没有真实故障诊断金标。备用机的振动/温度包含静止读数，需结合运行占比理解，不能把存在备用机解释为已自动投入。

## 工单草稿与确认边界

请求：`POST /api/alarms/15/work-order-draft`，手动记录耗时约 28 ms。

草稿 `fb08bbe3b2d04e57809559dcd6640e26` 含两个步骤：第一个来自已保存的 AI 核查建议，保留两条知识出处；第二个是跟踪恢复并记录结果的模板。草稿于演示时钟 18:44:56 生成，有效期 1800 秒，约 19:14:56 过期。原始 JSON 是历史验收存档，不能据此认为草稿仍可确认。

线上验收没有调用确认写入接口，收尾快照中的工单总数为 0。确认派单、一次性消费、重复派单冲突、开始处理、必填处理结果以及告警关闭规则，均由独立 `shuiwu_test` 库集成测试覆盖。

人工使用时，先查看草稿，在 `/docs` 的 `POST /api/work-orders` 中提交 `draft_id` 和负责人，可修改标题与步骤。同一告警最多有一张未关闭工单。状态流转为待处理 → 处理中 → 已关闭；关闭工单时数据已经恢复才一并关闭告警，工单关闭不代表过程数据已恢复。

## P04 风机故障实时验收

场景在 18:01:06 注入，指定 P04，持续 60 分钟，演示时钟为 1 倍速。设备前 30 分钟振动和温度爬升，随后跳停，场景结束后恢复。下表推送时间是订阅端接收的北京时间（按分钟列示），事件开始/恢复时间是演示时钟的 5 分钟桶起点，不能混用。

| 告警 | 事件开始 | 首次推送 | 数据恢复 | 恢复推送 |

| #23 振动异常 | 18:15 | 18:25；18:30 从预警升为告警 | 19:00 | 19:15 |

| #26 出水氨氮超标 | 18:50 | 19:00 | 截至 19:23 快照尚未确认恢复 | — |

场景注入到首次设备告警约 24 分钟。设备恢复后需连续三个正常运行桶才确认温度/振动恢复，停机事件只需一个；因此它们的恢复时间相同，但推送确认时间不同。停机期间无运行振动数据，没有被提前当成设备正常。19:20 时 DO 已恢复、氨氮仍约 6.6 mg/L，超过 Demo 限值，符合模拟器中的过程滞后；记录没有将它标为已恢复，也没有人工关闭这些告警。

`runtime-snapshot.json` 取于 19:23:04，保存健康检查、演示时钟、巡检、P04 与零工单状态；实时记录归档共 10 条变化。它是一次快照，后续运行状态以 API 为准。

归档后另做了离线复核：17 处引用的数据单元格/列名或知识摘录全部匹配；将三份原始叙述与冻结事实交给当前校验器，#1 命中 1 处范围问题，#2 命中 1 处重复单位，#3 无校验错误。此检查没有重新调用模型，也没有改写历史报告。
