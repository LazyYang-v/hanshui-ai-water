# M4：告警、工单与运行报告

## 告警规则与事件生命周期

巡检每 **10 秒**读取演示时钟，以已写满的 **5 分钟桶**判定；厂站指标取桶内均值，设备振动和温度取运行期间最大值。以下 `on/off` 表示确认触发/恢复所需的连续有效桶数，无数据的桶不计数也不打断。阈值属于 Demo 运行管理口径，出水限值见指标目录。

| 规则 | 条件 | 级别 | on/off |
| --- | --- | --- | --- |
| `effluent_exceed` | 出水 COD、氨氮、总氮、总磷、SS 任一超过限值 | 告警 | 2/3 |
| `effluent_trend` | 近 60 分钟线性拟合；至少 9 点、覆盖 40 分钟，R² ≥ 0.5，拟合值 ≥ 限值 50%，预计 120 分钟内超标 | 预警 | 2/3 |
| `do_low` | 好氧区 DO < 1.0 mg/L | 告警 | 2/3 |
| `inflow_surge` | 进水量 > 判定桶整点以前 7 天同钟点中位数的 1.5 倍 | 预警 | 3/3 |
| `inflow_load` | 进水 COD/TN/氨氮质量负荷 > 历史中位数 1.5 倍，且浓度 > 1.25 倍；两者均须超过中位数 + 3×1.4826×MAD | 预警 | 3/3 |
| `dosing_anomaly` | 近 60 分钟投药均值 > 负荷模型预期的 1.3 倍 | 预警 | 3/6 |
| `device_vibration` | 振动 > 4.5 mm/s；事件峰值 > 7.1 mm/s 升级 | 预警/告警 | 2/3 |
| `device_temp` | 温度 > 75 ℃；事件峰值 > 80 ℃ 升级 | 预警/告警 | 2/3 |
| `device_stop` | 非备用的鼓风机、提升泵、回流泵、加药泵整桶未运行 | 告警 | 1/1 |

同一持续异常按厂站、设备、规则、指标与时间重叠合并，保留原始触发值，更新最不利值、级别及恢复时间。趋势预警遇到实际超标立即结束，超标事件另行确认。`ended_at` 是数据恢复时间，`status` 是人工处理状态；数据恢复不会自动把告警改成“已关闭”。

启动先补扫 7 天，历史变化只发一条 `backfill` 汇总；之后扫描最近 3 小时，并额外回看 60 分钟作滑动窗口历史。有未恢复告警时，从其中最早的开始时间重放，超过 7 天也不截断。恢复必须由规则状态机数够有效正常桶，不再用“其他列已有后续数据”兜底判恢复；需保留事件开始以来的原始历史，长事件会增加扫描开销。Redis 锁防止多实例同时扫描，`alarm:events` 经 `/ws/realtime` 推送 `new`、`escalated`、`recovered`。

所有自适应基线按**判断桶所在整点之前**的近 7 天完整小时计算，不含该桶所在小时及未来小时；扫描同一窗口中的不同历史桶各用自己的基线。过去异常仍可进入历史，由稳健统计压低影响，不依赖模拟场景标签删样本。小时聚合直接查原始表，迟到数据无需等待连续聚合刷新。新事件保存条件确认时间 `condition_confirmed_at` 和实际首次发现的扫描时间 `detected_at`，检出延迟使用后者。

负荷按同一采样的 `inflow_m3h × 浓度 ÷ 1000` 先算 kg/h，再取 5 分钟均值；不能用流量均值乘浓度均值替代。COD、TN、氨氮分别登记为 `cod_load_kgh`、`tn_load_kgh`、`nh3n_load_kgh`，在 `/api/metrics` 的 `derived` 组展示，原始浓度字段仍为 mg/L。同钟点至少 3 个历史小时才评估；同时要求负荷和浓度上升，使单纯雨天稀释不触发浓度型冲击。水量与浓度同时升高则保留预警并注明模式，不能自动认定是上游偷排。该规则不代表出水已超标。

药耗模型用近 7 天小时数据做最小二乘，按 3 倍 MAD 剔除离群后重拟合：碳源使用进水量×TN、进水量×COD 与进水量，PAC 使用进水量×TP、进水量×COD 与进水量。至少需要 24 个有效小时；进水超过同时段基线 1.3 倍及其后 60 分钟、预期投药不足常态中位数 30% 时暂停评估。当前模拟数据拟合 R² 约 0.998–0.999，是模拟器按相近负荷关系前馈投药所致，不能作为真实厂站建模效果。

## 离线评测与对照

```bash
cd backend
uv run python -m evals.alarms.run --label another-60s --seeds 3 --step 60 --tune
uv run python -m evals.alarms.run --label another-5s --seeds 1 --step 5
uv run python -m evals.alarms.smoke --label another-api  # 独立真实Uvicorn/HTTP验收
```

脚本逐种子重建独立的 `shuiwu_alarm_eval` 库，不修改演示库，不调用模型；结果必须使用新标签，不能覆盖既有文件，也不要并发重建同一评测库。每个种子生成 7 天历史和 6 天评测数据：8 个异常场景、1 场阴性小雨，最后一天无事件。每 5 分钟推进演示时钟，实际调用生产 `scan → detect → persist/plan`，包含 6 小时停机。预载聚合只节省重复取数，历史切窗和逐时基线与生产共用，每组另在 6 个时刻逐字段对照原始 SQL 路径；浮点尾差容差为 1e-9。迟到、缺失和超过 7 天未恢复另用真实增量写库验证。检出延迟从场景开始算到实际扫描首次写入，包含补扫等待。

## 处置建议与确认派单

处置建议按告警类型固定查询工艺趋势、前后 6 小时同厂告警及相关设备，再检索知识库；厂站指标告警另追加同一窗口的固定统计事实，既有证据 ID 保持稳定。无需模型生成 SQL 或规划工具，复用 Agent 的三类引用校验；原因写为“待核查”，核查建议附知识出处。模型未配置返回 503，生成失败返回 502，同一告警正在生成返回 409；成功建议连同证据表和模型信息保存。

工单草稿仅存 Redis，30 分钟过期；步骤取自已保存的 AI 核查建议并保留引用（从对话生成时优先取该轮回答的核查建议），没有建议时明确使用模板，嵌入的西文指标名前后补空格（“复核出水 SS 在线仪表读数”）。**用户确认负责人、标题与步骤后**调用 `POST /api/work-orders` 才写库，草稿一次性消费；同一告警最多有一张未关闭工单。工单按待处理 → 处理中 → 已关闭流转，关闭必填处理结果。关闭工单时若数据已恢复，一并关闭告警；仍异常则保持人工处理状态，并提示继续跟踪。有未关闭工单的告警不能直接关闭。AI 助手里的派单入口复用同一草稿与确认流程（见 Agent 一节）。

```bash
curl -s localhost:8000/api/alarms?plant=P06
curl -s -X POST localhost:8000/api/alarms/15/advice
curl -s -X POST localhost:8000/api/alarms/15/work-order-draft
# 人工检查草稿后，在 /docs 的 POST /api/work-orders 填入 draft_id 与 assignee 并确认。
```

2026-11-07 对 P06 氨氮超标告警 #15 的真实验收：`deepseek-flash` 用时约 **5.1 秒**，4133+902 tokens，5 条陈述、17 处引用，首轮通过校验；工单草稿约 28 ms。验收只生成草稿，演示库工单数仍为 0；确认、重复提交与关闭流程由独立测试库集成测试覆盖。

## 日报/周报与叙述校验

```bash
curl -s -X POST localhost:8000/api/reports \
  -H 'Content-Type: application/json' -d '{"kind":"日报","date":"2026-11-06"}'
curl -s localhost:8000/api/reports/3/markdown
curl -s -o report.pdf localhost:8000/api/reports/3/pdf
```

日报覆盖指定日，周报覆盖截至指定日的 7 天，结束时间不超过演示时钟。SQL 先汇总水量、曝气电耗、药耗、达标率、异常事件和工单；模型只写 `{{事实id}}` 占位符，服务端替换成带单位的数值并生成表格。检查未知占位符、模型自行书写的数字、重复单位，以及范围、“均为”、最高/最低和“低于其他厂站”等关系。跨厂站范围用服务端算好的 `plants.*.min/max`，满达标厂站数用 `plants.compliance.full_n`。没有明显降雨时，降雨事实不送入模型。校验最多修复一次；模型不可用或仍失败就使用模板，并记录原因。

报告的水量、电量、药量按有数据的 5 分钟桶估算积分；达标率要求桶内原始点的出水五项均达标，按有效桶时间加权；各指标的超标时长和最高值另按 5 分钟均值统计。这两种口径不应互相倒算，缺失数据不当成达标。

PDF 由服务端用 reportlab 从同一份 Markdown 排版（标题、说明框、表格、分页页脚），不再调用模型，内容与 Markdown 下载一致。中文用 reportlab 内置的 Adobe CID 字体 STSong-Light，镜像不装字体文件，PDF 约 8 KB；阅读器需支持 Adobe-GB1 字体替换（Acrobat、Chrome、macOS 预览均可）。该字体缺 `³`、`·` 等字形，排版时改为上标或替换字符；西文和数字改用 Helvetica，避免 CID 西文字形过窄。日报 #4 两页，容器内首次请求约 1.6 秒（加载字体），之后约 0.26 秒。

11-06 日报的三次 Flash 实测保留了发现与修复过程：首份 4.71 秒，数字可追溯但范围漏掉最低的 P06；补充汇总事实和关系校验后，第二份 3.98 秒出现“6 座座”；加重复单位校验后，第三份首轮拦下 8 处重复单位，修复后通过，总计 **7.63 秒**、10040+1232 tokens。最终核对各厂站吨水曝气电耗范围为 **0.093–0.101 kWh/m³**，出水全时段达标厂站 **6 座**，P06 氨氮按 5 分钟均值超标 **2.5 小时**。这三次是指定场景验收，不能视为报告正确率评测。

2026-11-08 在前端页面上做了付费验收：告警 #25 处置建议 6.0 秒、5418+1378 tokens、29 处引用，首轮通过校验；11-07 日报 3.5 秒、4461+486 tokens，1 次尝试通过。验收中发现达标率与超标时长的口径说明没有写进报告正文，已补到报告开头。

建议、草稿、三版报告和实时告警验收说明见 [M4 API 验收记录](../backend/evals/ops/results/api-smoke.md)，其中保存了最终日报的冻结事实及运行快照。归档后离线核对 17 处引用全部匹配；当前报告校验器能分别拦下前两版的范围与单位问题，第三版无校验错误。

实时注入 P04 风机故障后，约 24 分钟收到首批温度/振动告警，随后出现停机、DO 偏低与氨氮超标。停机于 19:05 推送恢复，温度/振动于 19:15、DO 于 19:20 推送恢复；截至 19:23 快照，氨氮告警仍在跟踪中。设备恢复时间、规则确认时间和人工关闭状态分别记录，未将设备恢复等同于水质已恢复。

## 当前边界

线上与回放已统一逐时历史基线；过去异常可影响后续基线，稳健拟合不保证能隔离持续污染。正常巡检补扫最近 3 小时，更早的迟到数据需手动补扫，启动补扫仍为 7 天；已开放事件会延长扫描窗口，超过 7 天也保留，需保留原始历史。此前版本的告警与验收记录保留，不伪造其首次发现时间。质量负荷规则同时关注浓度，不覆盖所有稀释条件下的高水量风险；大流量由独立规则关注。AR(1) 噪声按步更新，60 秒与 5 秒分别验证。所有数字均为模拟数据开发评测；报告关系校验只覆盖指定句式，引用通过不证明全部语义正确。告警工单、报告与视觉巡检已有前端页面。只有一个管理员账号，派单时的负责人是自由填写的姓名，没有接人员台账。
